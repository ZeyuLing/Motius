# FlowHMR 队列、硬件预检与完整视频补测

Motius 0.3.14 / Blender 扩展 0.2.8，2026-10-27。使用用户提供的完整视频：25秒、30fps、750帧，输入 SHA256 `8f9e9c1193163940eafb512e9a0621a31fe316406e7a69aa3a357f6deceb17f1`。

## 可以直接使用的功能

- 独立队列服务和 SQLite 数据库，任务参数、人物轨迹和每次尝试落盘。同一队列串行执行；多个 Blender 实例共享默认数据库。
- 提交后继续选视频、检测人物、准备角色和编辑场景。队列可暂停后续任务、恢复、重排、取消、重试和分页查看历史；失败不阻塞后续 case。
- 关闭 Blender、加载其他 `.blend` 或禁用插件不终止后台任务。重启后重新连接；服务崩溃后先检查上一工作进程，避免重复运行。机器重启后未完成任务标为 Interrupted，等待手动重试。
- 结果完成不自动修改场景，点击 **Import result** 才导入当前场景。人物检测结果通过队列中的 **Choose person** 打开。
- 每次执行前检查 CUDA 设备及实际 BF16 执行、GPU 型号和当前空闲显存、视频规模、系统/容器可用内存、输出磁盘空间及 FFmpeg/FFprobe。检查结果与调度决策写入 `preflight.json`。
- CUDA OOM 后释放失败进程，再以较小工作批量新开一次完整尝试。最多自动重试4次；保留失败日志和参数。标准模式仅允许一次相同配置的新进程重试，不偷偷切换 Fast SAM 或流式 VGGT。

预检发生在排到任务时，以当时空闲显存为依据。显存规划是根据 H200 已测视频建立的保守估计，包含预留量；其他硬件、长视频和同时新增的显存占用仍可能失败。缺少原始 BF16 执行支持时明确拒绝，不自动转换成 FP16。CPU/MPS 不作为产品推理入口支持。

低显存模式的帧批量上限按空闲显存选择：小于8 GiB选1、小于12 GiB选4，其余选8，并尊重用户设置的更小上限。查询/FFN工作块对应选择1024/2048/4096。任务执行中出现 OOM 时，进一步减半工作批量和查询块；不会减少视频帧、手部特征、权重精度或采样步数。

同一 H200、4个 CPU 线程、同一选中人物和权重、20步采样、seed=0、TF32关闭、原有网络 dtype；重新执行完整相机和身体/双手特征，无前端缓存。下表均从选人后计时，包含模型加载，排除检测选人、Blender导入、网格转换、重定向、接地、导出与播放缓存准备。

普通模式使用 official SAM、reference VGGT、单帧特征提取和标准动作注意力；低显存模式还包含 Fast SAM、帧合批和流式执行，因此并非仅设置不同显存限额。普通模式本次允许100 GiB分配器预算；此前低显存记录设置6 GiB预算。后台原有两项服务始终保留，未停止。驱动显存按秒采样，可能遗漏瞬时峰值，不包含 Blender、桌面或其他服务。均为单次实测，不是多次吞吐统计，也不是消费级显卡结果。

普通模式启动时使用与发布片相同的神经计算代码；本次产品化只为 reference 路径增加可忽略的可选参数传递，未更改其计算。加载的代码身份单独保存。硬件预检与队列调度不计入模型加载起点后的上述推理时间。

## 真实 CUDA OOM 恢复

在 H200 上人为将 PyTorch 分配器预算限制为 **4.3 GiB**，运行完整750帧：

1. 第一次以 SAM/VGGT 帧批量8运行，相机处理完整750帧后，身体/双手阶段触发真实 `torch.cuda.OutOfMemoryError`。
2. 失败进程退出，队列读取结构化 `cuda_oom` 错误，新开进程；SAM/VGGT 帧批量降为4，VGGT查询/FFN块4096→2048，动作查询块256→128。
3. 第二次成功处理750帧，保留52关节身体与手部旋转，所有输出有限，帧 ID 与此前结果完全相同。成功尝试推理 **110.28秒**；包含第一次失败、进程启动、预检和输出的提交到完成总等待 **178.72秒**。
4. 成功尝试峰值分配3.91 GiB、驱动采样4.94 GiB。与此前8帧批量结果比较，输出中的22个世界关节点位置平均差 **0.516毫米**、最大差 **1.065毫米**。这是数值差异比较，不是真人动捕精度指标，也不是逐位一致性承诺。

这是分配器压力注入测试，验证的是自动恢复链路；不能据此宣称4GB/5GB消费卡可运行。CUDA上下文、图形界面和其他库占用不受该分配器限额覆盖。

## VGGT 的 N 帧合批

已通过统一 pipeline 暴露 `vggt_frame_batch_size`、`vggt_query_chunk_size`、`vggt_token_chunk_size`。帧编码与帧内注意力可以合批；跨帧注意力仍保留全部帧的 K/V，按查询块执行，未把长视频切成互不关联的独立时间窗。原始 dtype、图像分辨率、帧数与相机 interval=1 均保留。

N增大会增加图像、帧内激活和工作空间显存，未必持续加速；预检与OOM重试优先选择能完成任务的较小批量。帧批量1/2/8及全部全局键值的数值回归已经覆盖；完整视频的4帧恢复路径另有真实GPU验证。改变合批和注意力执行顺序仍可能产生浮点舍入差异。

## ONNX / TensorRT

当前发布后端仍是 PyTorch，没有已经验证并可交付的整条 FlowHMR ONNX/TensorRT 推理引擎。不能用“可导出”代替完整视频的速度、显存和输出对照。

可优先评估独立帧编码器等较稳定子图，继续由 pipeline 管理完整时序注意力、选人、图像几何和内存调度。工程上还需要处理动态序列长度、原始 BF16/FP32 dtype、算子覆盖、引擎构建缓存及回退，并对完整视频重新验收。这里不默认启用FP16/INT8，也不承诺换引擎必然加速。

TensorRT引擎有平台、版本与硬件兼容条件；ONNX Runtime GPU同样依赖匹配的CUDA/cuDNN环境。它们不能直接解决所有环境问题。参考 [NVIDIA引擎兼容说明](https://docs.nvidia.com/deeplearning/tensorrt/latest/inference-library/engine-compatibility.html) 和 [ONNX Runtime CUDA要求](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。

## 验证与边界

79项定向回归通过。真实 Blender 4.5.3 / Linux 验证阶段进度、场景清理后任务继续、结果手动导入52关节且 Blender 不导入Torch；另一次真正退出Blender的验证中，退出时两任务分别Running/Queued，退出后都完成。两种ZIP均通过Blender扩展校验。

Windows分支包含独立进程、文件锁与创建时间校验，但本轮没有Windows或消费级显卡实机验收。默认共享数据库负责同一调度域串行化；另建不同数据库的队列不协调同卡资源。用户显式导入后的骨架创建与烘焙仍占用Blender主线程。
